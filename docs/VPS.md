# Розгортання на KVM VPS (AlmaLinux 8 + Webuzo)

Система вже розгорнута і працює: **<http://45.94.157.110>**

Цей документ описує, що саме стоїть на сервері, чому саме так, і як оновлювати.

---

## Що працює зараз

| Компонент | Де |
|---|---|
| Фронтенд (React/Vite, статика) | Nginx, `/var/www/html` |
| Бекенд (FastAPI/Uvicorn) | `127.0.0.1:8000`, systemd-юніт `estimator` |
| Публічний вхід | Nginx на `:80`, `/api` → uvicorn |
| Код застосунку | `/opt/estimator/src` |
| Virtualenv (Python 3.11) | `/opt/estimator/venv` |
| База, завантаження, кеш сторінок | `/var/lib/estimator` |
| Панель Webuzo | `https://45.94.157.110:2005` (без змін) |
| Apache від Webuzo | перенесений з `:80` на `:8080` |

Обидва сервіси (`estimator`, `nginx`) увімкнені в systemd і перевірені
перезавантаженням сервера.

## Порт 80 і Webuzo

Webuzo ставить власний Apache і за замовчуванням віддає йому `45.94.157.110:80`.
Nginx не міг би зайняти цей порт, тому Apache перенесено на `:8080`:

```
/usr/local/apps/apache2/etc/conf.d/webuzo.conf     Listen 80  -> Listen 8080
/usr/local/apps/apache2/etc/conf.d/webuzoVH.conf   :80        -> :8080
```

Оригінали збережено поруч із суфіксом `.bak-preestimator`. Сайтів на Apache не
було (`/home` порожній, жодного vhost), тому перенесення нічого не зламало —
панель Webuzo слухає окремі порти 2002–2005 і працює як раніше.

### Це не тримається саме по собі

Припущення, що правки конфігу достатньо, виявилось хибним. У ніч на 03.09
сайт віддавав дефолтну заглушку Webuzo. Журнал показує рівно, що сталося:

```
Sep 03 00:00:03  httpd.conf, webuzo.conf, webuzoVH.conf перезаписані  (Listen 80 повернувся)
Sep 03 00:00:06  nginx.service: Main process exited, code=killed, status=9/KILL
Sep 03 00:00:06  /usr/local/apps/apache2/bin/httpd -k restart
```

Два окремі механізми, і кожен вимагає свого захисту:

1. **Webuzo перегенеровує конфігурацію Apache цілком** — не редагує, а
   переписує всі три файли. Будь-яка правка `Listen` живе до наступного
   нічного запуску. Шаблон, з якого це генерується, у дереві Webuzo у
   відкритому вигляді не лежить, тож «полагодити джерело» неможливо.
2. **Процедура перезапуску Webuzo вбиває процеси за іменем** — `nginx`
   потрапляє під роздачу разом із панельним. Системний Nginx отримав
   `SIGKILL`, а юніт не мав `Restart=`, тому просто лишився мертвим.

### Перша спроба була помилковою

Спершу захист складався лише з автоперезапуску Nginx і вартового, який раз на
хвилину віднімав `:80` в Apache. Це не спрацювало — і провал був повчальний.

Моніторинг Webuzo теж працює **щохвилини**: він бачить, що Apache зупинений
(«PID FILE Missing»), і піднімає його знову. Вийшла нескінченна дуель двох
таймерів: за 18 годин — понад 10 000 подій Nginx, аж до `core-dump`, і сайт,
який то з'являвся, то зникав.

Висновок простий: із панеллю не можна змагатися за ресурс. Треба зробити так,
щоб вона перестала його забирати.

### Що працює: незмінний конфіг

Джерело Webuzo зашифроване (ionCube), тож вимкнути моніторинг Apache зсередини
неможливо. Натомість блокується сам файл, який панель переписує:

```bash
cd /usr/local/apps/apache2/etc/conf.d
chattr -i webuzo.conf webuzoVH.conf     # зняти блокування, щоб правити
sed -i 's/^Listen 80$/Listen 8080/' webuzo.conf
sed -i 's/45.94.157.110:80>/45.94.157.110:8080>/' webuzoVH.conf
chattr +i webuzo.conf webuzoVH.conf     # заблокувати назад
```

Прапорець `i` (immutable) не дає змінити чи замінити файл навіть root'у, доки
його не знято. Регенерація Webuzo просто не може перезаписати порт, тому Apache
щоразу стартує на `:8080`. Його PID-файл на місці, моніторинг задоволений і
нікого не перезапускає — дуель зникає замість того, щоб її вигравати.

**Важливо:** перед будь-яким майбутнім редагуванням цих двох файлів (і перед
оновленням Apache через панель) треба зняти `chattr -i`, інакше зміна тихо не
застосується. Перевірити стан: `lsattr /usr/local/apps/apache2/etc/conf.d/`.

### Підстраховка

`deploy/vps/nginx-restart.conf` → `/etc/systemd/system/nginx.service.d/restart.conf`

`Restart=always`, `RestartSec=2`. Nginx більше не може лишитись убитим.
Самого цього замало: якщо Apache уже зайняв `:80`, перезапуск падає з
`code=exited status=1`.

`deploy/vps/port80-guard.{sh,service,timer}` → `/usr/local/sbin/` і
`/etc/systemd/system/`

Раз на хвилину перевіряє, хто тримає `:80`. Якщо це Apache — зупиняє його;
якщо Nginx не слухає — піднімає. Навмисно вузький: Apache на `:8080` не чіпає,
тому після блокування конфігу він більше не спрацьовує взагалі — лишається
чистою підстраховкою на випадок, якщо прапорець `i` колись знімуть.

Перевірено відтворенням аварії — `Listen 80` повернуто, `pkill -9 -x nginx`,
`httpd start`:

```
11:17:01  nginx убито; автоперезапуск провалився (Apache тримає :80)
11:17:02  port80-guard: Apache has taken :80 back — stopping it
11:17:04  nginx піднявся і зайняв :80
```

Відновлення — близько трьох секунд, без втручання. Найгірший випадок —
до хвилини, поки не спрацює таймер.

### Стан після перезавантаження

Автозапуск Apache вимкнено (`chkconfig httpd off`, усі рівні `off`), але Webuzo
однаково піднімає його своїм `webuzo-onboot`, повз systemd. Це не проблема:
конфіг переживає перезавантаження, тому Apache стартує **на `:8080`**, а Nginx
спокійно бере `:80`. Перевірено ребутом: `:80` — nginx, `:8080` і `:443` —
httpd, `:2005` — панель.

### Якщо захочете прибрати цю конструкцію

Правильне рішення без вартового — задати порт Apache у самій панелі Webuzo
(Apache Settings), щоб регенерація одразу писала `8080`, або зовсім прибрати
Apache з Webuzo, якщо сайти на ньому не плануються. Тоді
`port80-guard.timer` можна вимкнути:

```bash
systemctl disable --now port80-guard.timer
```

## Ліміт на розмір завантаження

`client_max_body_size` встановлено в **450M**, а не в 150M.

Причина конкретна: реальний пакет креслень клієнта
(`Ружена_та_Антон_Скнилів_Пакет_креслень.pdf`) важить **161 MiB**. З лімітом
150M Nginx відхиляв його з `413 Request Entity Too Large` ще до того, як запит
доходив до бекенду — це перевірено на сервері.

450M узгоджено з `MAX_UPLOAD_MB=400` у `.env` плюс запас на multipart. Так
реальне рішення про відмову ухвалює бекенд, який повертає зрозуміле українське
повідомлення («Файл більший за 400 МБ»), а не голу HTML-сторінку Nginx.

Щоб змінити ліміт, правити треба **обидва** значення:

```
/etc/nginx/conf.d/estimator.conf   client_max_body_size
/opt/estimator/src/.env            MAX_UPLOAD_MB
```

## `VITE_API_BASE_URL` має бути **порожній**

Це не дрібниця конфігурації, а найлегший спосіб покласти весь інтерфейс.
`src/api.ts` будує кожен запит так:

```ts
export const API_BASE = (import.meta.env.VITE_API_BASE_URL ?? "").replace(/\/$/, "");
function url(path: string) { return `${API_BASE}/api${path}`; }
```

`/api` **вже додає код**. Якщо зібрати фронтенд із
`VITE_API_BASE_URL=http://45.94.157.110/api`, браузер піде на
`/api/api/dashboard` і отримає `404` на кожен виклик — сторінка при цьому
відкривається, але лишається порожньою, бо дані не приходять. У логах Nginx це
видно одразу за подвоєним префіксом.

Тут фронтенд і API живуть на одному origin за Nginx, тому правильне значення —
порожній рядок: запити йдуть відносними шляхами `/api/...`. Це також означає, що
бандл не треба перезбирати після переїзду на домен або HTTPS.

Абсолютне значення потрібне лише тоді, коли фронтенд хоститься окремо від API
(наприклад, на Vercel), і тоді це **чистий origin без `/api`**:
`API_URL=https://api.example.com bash deploy/vps/redeploy.sh`.

`redeploy.sh` після збірки перевіряє бандл на `/api/api` і падає з помилкою,
якщо префікс подвоївся.

## Таймаути

`POST /api/projects/{id}/analyze` виконується **синхронно**: запит висить, доки
не завершиться весь AI-аналіз, а це хвилини на великому комплекті. Тому
`proxy_read_timeout` і `proxy_send_timeout` підняті до **1800s** — стандартні 60s
давали б `504` посеред нормального аналізу.

`proxy_request_buffering off` — щоб 160-мегабайтний PDF не записувався спершу
цілком у тимчасовий файл Nginx, а йшов одразу в uvicorn: обробник і так пише
його на диск шматками по 1 МБ.

## Один воркер uvicorn — навмисно

Сховище — SQLite у режимі WAL. Кілька процесів-письменників під час аналізу
впиралися б у `database is locked`. Паралелізм дають:

* пул потоків FastAPI (ендпоінти оголошені як `def`, не `async def`);
* `AI_MAX_CONCURRENCY=6` — паралельний аналіз сторінок усередині пайплайна.

Якщо колись знадобиться кілька воркерів — спершу переїзд на PostgreSQL через
`DATABASE_URL`.

## Оновлення

```bash
bash deploy/vps/redeploy.sh
```

Скрипт пакує робоче дерево, збирає фронтенд на сервері, підмінює каталог і
перезапускає `estimator`. `.env` і `/var/lib/estimator` він не чіпає, тож ключ
API і база лишаються на місці. Попередня версія лежить у `/opt/estimator/src.old`.

Вручну те саме:

```bash
systemctl restart estimator      # перезапустити бекенд
systemctl reload nginx           # перечитати конфіг Nginx
nginx -t                         # перевірити конфіг перед reload
journalctl -u estimator -f       # логи бекенду
tail -f /var/log/nginx/estimator.error.log
```

## Конфіги в репозиторії

`deploy/vps/` містить точні копії того, що стоїть на сервері:

| Файл | Куди |
|---|---|
| `nginx.conf` | `/etc/nginx/nginx.conf` |
| `estimator.conf` | `/etc/nginx/conf.d/estimator.conf` |
| `estimator.service` | `/etc/systemd/system/estimator.service` |
| `nginx-restart.conf` | `/etc/systemd/system/nginx.service.d/restart.conf` |
| `port80-guard.sh` | `/usr/local/sbin/port80-guard.sh` |
| `port80-guard.service` | `/etc/systemd/system/port80-guard.service` |
| `port80-guard.timer` | `/etc/systemd/system/port80-guard.timer` |
| `redeploy.sh` | запускається локально |

Стоковий `nginx.conf` збережено на сервері як `/etc/nginx/nginx.conf.stock-bak`.
З нього прибрано дефолтний `server`-блок: він займав `:80` під
`/usr/share/nginx/html` і перекривав би vhost застосунку.

## Що варто зробити далі

**HTTPS.** Зараз усе по HTTP, і `VITE_API_BASE_URL` вшитий у бандл як
`http://45.94.157.110/api`. Для сертифіката потрібен домен — на голий IP
Let's Encrypt сертифікат не видає. Коли домен буде:

1. навести A-запис на `45.94.157.110`;
2. звільнити `:443` від Apache (аналогічно до `:80` — перенести на `:8443`);
3. `dnf install certbot python3-certbot-nginx && certbot --nginx -d домен`;
4. перезібрати фронтенд з `VITE_API_BASE_URL=https://домен/api`
   (`API_URL=https://домен/api bash deploy/vps/redeploy.sh`).

**Автентифікація.** API відкритий: будь-хто, хто знає IP, може створювати
проєкти, завантажувати документи й запускати аналіз — тобто витрачати ваш
ключ Anthropic. До того, як адресу отримає хтось сторонній, потрібен хоча б
базовий захист (HTTP Basic на рівні Nginx — найдешевший варіант).

**Резервні копії.** Уся робота живе в `/var/lib/estimator`. Достатньо
періодично копіювати цей каталог.
